**Active Story:** Sprint 4 | PRO-001 | Create My Business or Freelancer Listing

**Story:**
As a user who wants to offer a service, I want to choose whether I'm a Business or a Freelancer and enter my core details, so that I can list my business or service on the platform for free.

This is the first story of Sprint 4 and the first story of a genuinely new domain (`provider`) — no `backend/app/modules/provider/` or mobile `features/provider/` code exists yet. It builds the Provider aggregate root plus the first half of the onboarding flow (`14_USER_FLOWS.md` Flow 2, steps 1–5): type selection (immutable — a Provider is exactly one subtype, never both) and subtype-specific details. It reuses the caller's existing Account rather than creating a new one.

**Scope boundary:** does NOT include portfolio/availability management (`portfolios`, `provider_availability`, `service_areas` — PRO-002) or the Verification gate (documents, OCR, admin review — VER-001). A Provider created here is never discoverable (`is_discoverable` stays `false`). Does NOT include the Category domain/taxonomy — see the `category_label` decision below. Does NOT include Claim-Your-Listing, the Provider Dashboard, or Storefront/Edit Profile (S-25) — no update endpoint of any kind exists in this story.

## Technical Context & Architecture Constraints

- `docs/AI/04_DATABASE.md` already fully specifies `provider.providers`, `provider.business_profiles`, `provider.freelancer_profiles`, and the `provider_type`/`listing_source`/`verification_status` enums — implement column-for-column, with one flagged addition (see below).
- **Endpoint shape is a `/providers/me` singleton per ADR-015** (`GET`/`POST /providers/me`, no `{id}` ever) — a Provider is inherently 1:1 with an Account (AC8), not a `{id}`-addressable collection like `saved_addresses`. `POST` is submitted exactly **once**, at the end of the mobile wizard, containing type + basic info + subtype details together — do not build incremental per-step `PATCH` endpoints or any server-side draft/partial-provider state; `providers.display_name` is `NOT NULL`, so a partial row after type-selection alone can't validly exist.
- **One-Provider-per-Account and type immutability (AC3/AC8/AC10):** `ProviderService.create_provider` must check `ProviderRepository.get_by_user_id(user_id)` first and raise a new `ProviderAlreadyExistsError` (409) if a row already exists, **regardless of the requested `provider_type`** — this single check is what makes type immutable (a second call with a *different* type must be rejected exactly like a second call with the *same* type). Add `04_DATABASE.md`'s already-specified `uq_providers_user_id` partial unique index as defense-in-depth. This story builds no update endpoint for `providers` at all, so there is no other code path that could ever change `provider_type`.
- **Cross-module role grant — new pattern, `provider → identity` (reverse of ADR-014's `identity → customer`/`identity → audit`):** add a new, single-purpose `RoleAssignmentService` inside `identity` (`ensure_role_assigned(user_id, role_name)` — idempotent, checks existing roles first, inserts a `UserRole` row only if missing, flush only). `ProviderService.create_provider` takes this as a constructor dependency and calls it to grant `ROLE_PROVIDER`, on the same session as the `providers` row it just created. Wire it via a new `get_role_assignment_service()` in `identity/dependencies.py`, imported into `provider/dependencies.py` — mirroring exactly how `customer/dependencies.py`'s `get_customer_service` is imported into `identity/dependencies.py` today, just reversed. Do **not** modify `AuthService`'s existing inline role-assignment logic — this is a new, separate capability, not a refactor of already-shipped code. Modules must never import another module's repository directly (`02_ARCHITECTURE.md`) — `provider` must depend on this new identity **service**, never on `RoleRepository` directly.
- **Category field — the Category domain does not exist yet** (`categories`/`provider_categories` tables, `13_OPEN_DECISIONS.md` item 1). AC4 still requires capturing "category" as part of basic info. Add a new, flagged, temporary column: `providers.category_label VARCHAR(100) NOT NULL` — plain free text, no taxonomy validation. This is a genuine addition beyond `04_DATABASE.md`'s literal `providers` spec (mirroring CUS-002's precedent of flagging a beyond-doc schema addition rather than silently improvising) — flag it in the migration/model docstrings and note it needs a `04_DATABASE.md` follow-up update at story close.
- **Defaulting (AC7/AC10):** every newly created `providers` row gets `verification_status=pending` and `is_discoverable=false` unconditionally — no request field can influence either. Test this explicitly for **both** subtypes, not just one.
- **`slug`/`country_code` are server-derived, never client input:** `slug` = slugified `display_name` + a short random suffix, retried on a uniqueness collision (not in AC4's field list; deep-link sharing is a later MVP stage). `country_code` on `providers` is copied up from whichever subtype's location the **mobile client** already reverse-geocodes via the existing `LocationPickerScreen`/`LocationPickResult.countryCode` (same established pattern as `saved_addresses.country_code` from CUS-002) — it travels as a request field inside `business_details`/`freelancer_details`; no new backend geocoding capability is introduced.
- **Reuse `LocationPickerScreen` unmodified** (`mobile/lib/shared/widgets/location_picker/`) for both the Business address pin (S-18a) and the Freelancer base-location pin (S-18b) — it was built generic and Customer-domain-free specifically for this reuse (confirmed directly in the CUS-002 code). Zero new mobile dependencies; `google_maps_flutter`/`geolocator`/`geocoding` are already in `pubspec.yaml`.
- **Mobile wizard state (AC3/AC9):** one in-memory Riverpod controller (`ProviderOnboardingController`) holds the draft across S-16 (Choose Type) → S-17 (Basic Info) → S-18a/b (subtype details); no route-`extra` passing, no cross-app-restart persistence in this story (the multi-day-resumability guideline in `16_UX_GUIDELINES.md` targets the future Verification step, not this short sub-flow). Only the final step submits, once.
- **Step indicator (AC9):** build a new, generic `mobile/lib/shared/widgets/step_indicator.dart` (this codebase's first multi-step-form indicator) — no domain coupling, so any future multi-step flow can reuse it, mirroring `LocationPickerScreen`'s own precedent.
- Full detail, file-by-file, is in `docs/implementation/plans/Plan_S04_PRO-001.md` — follow it, including all 9 numbered Architecture Decisions and the Verified Current State section.

3. Add `backend/app/modules/provider/repositories/`: `provider_repository.py` (`get_by_user_id`), `business_profile_repository.py`, `freelancer_profile_repository.py` — all `BaseRepository[T]` subclasses.

5. Add `backend/app/modules/provider/services/provider_service.py`: `ProviderService(provider_repository, business_profile_repository, freelancer_profile_repository, role_assignment_service)` with `get_my_provider(user_id)` and `create_provider(user_id, *, payload)` — existence check → 409 if present (regardless of type), slug generation, `providers` + subtype-profile row creation with hardcoded defaults, `ensure_role_assigned(user_id, ROLE_PROVIDER)`, all flush-only on one session.

9. Add `backend/app/modules/provider/dependencies.py`, importing `get_role_assignment_service` from `app.modules.identity.dependencies`.
10. Register the router in `backend/app/api/v1/api.py` (`prefix="/providers"`). Add `import app.modules.provider.models` to `backend/tests/conftest.py`'s `db_engine` fixture (ADR-013 pattern).

Write tests: `test_provider_service.py` (defaults for both subtypes; same-type second-creation → 409; **different-type** second-creation → 409, proving type immutability; role-grant idempotency; slug uniqueness), `test_provider_endpoints.py` (happy path both subtypes; AC2's "no new auth step" via reused JWT; 409 on duplicate; `GET` 404-then-200; 401 unauthenticated; 422 on mismatched subtype details), `test_role_assignment_service.py` (grant, idempotent no-op, doesn't remove existing roles).

## Definition of Done

- All 10 acceptance criteria in `docs/AI/Project_Tracker.xlsx` (PRO-001 row) are met, verified by `tester` against each one individually — see the Plan's Verification Plan table for exactly what each AC's test must prove.
- `providers`/`business_profiles`/`freelancer_profiles` match `04_DATABASE.md` column-for-column, plus the new flagged `category_label` column; migration upgrade/downgrade both verified.
- An already-authenticated caller can create a Provider linked to their own Account with no new registration/OTP/OAuth step (AC2).
- Provider type is chosen exactly once via a dedicated screen and cannot be changed afterward — proven by a second-creation attempt with a *different* type being rejected the same way a same-type duplicate is (AC3/AC8/AC10).
- Basic info is captured before subtype-specific details, on both the Business and Freelancer paths, matching AC4/AC5/AC6 field-for-field.
- Every newly created Provider defaults to `verification_status=pending`/`is_discoverable=false`, regardless of subtype or any request input (AC7/AC10).
- A visible step indicator appears on every step screen, and no step requires more than its minimal, AC-specified fields to proceed (AC9).
- No PRO-002/VER-001/Category-domain/Claim-Your-Listing/Dashboard/Storefront/Quote/messaging/payment functionality is introduced, even incidentally.
- Backend and mobile automated test suites pass; lint/format clean on both sides.
- Upon `tester`/`architect` clean verdicts, pause for explicit user sign-off before the Walkthrough is written or the changelog/tracker is touched.
